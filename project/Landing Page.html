// Operating principles

P/01
Boring tech, sharp execution.

Choose the dullest tool that solves the problem; spend the saved attention on the hard parts that nobody wants to debug at 2am.

P/02
Tests as documentation.

If a test wouldn't read like a paragraph from the README, the API is probably wrong. Refactor the API, not the test.

P/03
Optimize for the next reader.

Including (especially) future-me, three months from now, who has forgotten everything and just wants to ship one fix.

P/04
Ship small, ship often.

Tiny green CIs beat large red ones. A merged hundred-line PR is worth ten thousand-line drafts in a stale branch.
